# 单卡服务性能与真实级联测量

2026-11-02 · 冻结 `solo-v1` benchmark · 单张 NVIDIA L40S · BF16

**在这次单卡、预热后的固定分类工作负载上，StartLux 直接服务兼具较高准确率与较低延迟。** 相比 Qwen，串行吞吐为其 3.42–3.63 倍，8 并发吞吐为其 1.81–1.88 倍。级联收益取决于转交比例和并发条件；Kev → Qwen 在串行 CLINC 上节省部分时间，但在 8 并发的两个任务上都比直接 Qwen 吞吐更低、P95 更高。

这些倍率对应当前硬件、接口、输出格式和负载。它们不是模型通用生成速度的比较，也不能外推成所有部署条件下的优势。

## 1. 测量与复核范围

共核对 **60 个计时单元**，来自 2 个任务 × 5 个部署 × 2 个客户端并发数（1、8）× 3 轮。每个任务有同一组 **200 个唯一主测试样本**，由冻结的 `select_benchmark` 在读取模型预测之前确定：CLINC 为每个银行意图 10 条及 OOS 50 条；SQuAD 两类各 100 条。所有部署、并发和轮次使用相同 ID 及顺序。

每轮完整循环该 200 条工作负载，直到已运行至少 30 秒；本次每轮 2–9 个循环，耗时 **30.14–56.12 秒**。计时 trace 共 **60,200 次用户级输入**，其中 3,520 次触发后级，因此留下 **63,720 次底层 HTTP 调用**。所有调用均首次成功，没有重试、终止错误或复用请求 ID。

独立复核从每条 trace 的原始响应重新解析标签/概率，按冻结的 refitted 温度及门限重算路由，核对每个循环的 200 条样本，并重新计算 P50、P95、准确率、转交率和吞吐公式。60 个单元全部通过；配置、校准及 benchmark 源码指纹一致。初始开发集负载验收还覆盖了 10 个任务/部署组合，每组 64 条开发样本，并选择共同支持的并发数 8。

### 数值的含义

- **延迟**从线程池 worker 开始执行 `cascade_call` 到得到最终结果，包含本次实际 HTTP 服务等待、前级及必要的后级时间；不包含 200 个任务提交后、尚未获得 worker 的控制器线程池排队时间。不能将它直接解释为开放流量下用户从提交开始的完整排队延迟。
- **吞吐**为一轮完成的输入数除以该轮记录的总 wall-clock 时间，包含整个循环调度过程。所有输入成功，所以成功吞吐与总吞吐相同。trace 没有独立的起止时间戳，本次复核验证了该分母下的公式，不能重新测量已经结束的 wall-clock。
- **预热和模型启动**不在计时区间内。每个任务计时前使用开发集预热；这是热服务测量。
- 下表先在每轮 trace 内计算分位数，再对 **3 轮的 P50/P95 或吞吐取算术均值**；方括号为三轮最小值与最大值。它们不是合并所有请求后的分位数，也不是 95% CI。完整均值和范围均保存在 [summary.csv](summary.csv)。

| 任务 / 并发 | 吞吐倍率：StartLux / Qwen | P50 比值：Qwen / StartLux | P95 比值：Qwen / StartLux |

并发提高吞吐的同时也增加单请求延迟。例如 StartLux/CLINC 从约 26.02 输入/s 增至 59.10 输入/s，P95 则从约 38.90 ms 增至 137.57 ms。因此应根据吞吐和尾延迟的共同要求选择负载，不能将并发提升等同于每条请求变快。

Kev/SQuAD 在 8 并发的第一轮明显较慢：P95 为 410.55 ms，另两轮约 202.33、202.70 ms；吞吐分别为 38.16、46.45、46.29 输入/s。报告保留三轮及其范围，没有排除较慢轮次。当前 trace 不能确定该波动的具体系统原因。

## 3. 级联的质量、转交率与代价

下表是这 200 条性能工作负载循环中的轮次均值，不能替代完整正式测试集的准确率。两条级联实际执行前级，只有门限拒绝时才调用 Qwen；使用正式实验已冻结的 refitted 温度和阈值。

| 部署 | CLINC 准确率，c1 / c8 | CLINC 转交率，c1 / c8 | SQuAD 准确率，c1 / c8 | SQuAD 转交率，c1 / c8 |
|---|---:|---:|---:|---:|
| Kev | 80.00% / 80.00% | 0.00% / 0.00% | 81.00% / 80.53% | 0.00% / 0.00% |
| StartLux | 94.50% / 94.50% | 0.00% / 0.00% | 93.00% / 93.00% | 0.00% / 0.00% |
| Qwen | 88.50% / 88.50% | 0.00% / 0.00% | 87.50% / 87.50% | 0.00% / 0.00% |
| Kev → Qwen | 87.00% / 87.00% | 33.00% / 33.00% | 87.00% / 87.00% | 65.50% / 65.39% |
| StartLux → Qwen | 94.50% / 94.50% | 0.50% / 0.50% | 93.50% / 93.50% | 5.00% / 5.00% |

- **CLINC / Kev → Qwen**：转交 33%。串行吞吐比直接 Qwen 高 66.1%，但准确率为 87.0%，低于 Qwen 的 88.5%，且 P95 为 171.17 ms，高于 Qwen 的 145.19 ms。8 并发吞吐降为 Qwen 的 0.77 倍，P95 约为其 2.20 倍。较好的串行 P50 没有转化为高并发或尾延迟优势。
- **SQuAD / Kev → Qwen**：约 65.4–65.5% 的输入需要后级。串行吞吐仅比 Qwen 高 6.8%，P50 和 P95 均更高；8 并发吞吐只有 Qwen 的 0.56 倍，P95 约为其 2.47 倍。测得的准确率也略低于直接 Qwen。
- **CLINC / StartLux → Qwen**：仅转交 1/200，准确率与直接 StartLux 相同。级联吞吐相对直接 StartLux 在 c1、c8 分别减少约 3.8%、4.1%，并需要让两个模型同卡常驻。
- **SQuAD / StartLux → Qwen**：转交 10/200，准确率由 93.0% 到 93.5%，相当于该子集净多 1 条正确预测；吞吐相对直接 StartLux 在 c1、c8 分别减少约 15.6%、23.6%。完整正式测试中净增加 5/2,000，配对增益区间跨零，详见[正式结果报告](../formal-2026-11-02/RESULTS_ZH.md)，因此不能用这个反复循环的 200 条子集强化准确率显著性主张。

SQuAD/StartLux 级联转交率恰为 5%，P95 接近前级直接结束与进入后级请求的分界。P95 不代表后级请求自身的耗时，解释尾部服务要求时应保留这一点。

这里的质量和性能权衡是完整服务组合的实测结果。当前测量没有把额外开销分解为模型算子、服务排队、缓存或双模型同卡争用，因而不将单一机制写成已证实原因。

## 4. 并发下的标签与路由变化

并发没有导致运行失败，但不保证逐样本结果完全相同。

- SQuAD `squad:5727f6723acd2414000df0e9` 在 Kev 直接服务的 c1 中 14/14 次输出 `answerable`；c8 中 1/20 次为 `answerable`、19/20 次为 `unanswerable`。该样本真实标签为 `answerable`，使 Kev 的该工作负载准确率从 81.00% 降至三轮 80.50–80.58%，均值 80.53%。
- Kev → Qwen 中同一样本的前级标签也有变化，但后级使最终标签保持一致。另一条 `squad:572fe53104bcaa1900d76e69` 的路由在 c8 中 2/9 次由转交变为接受，因此三轮平均转交率约为 65.39%，而 c1 为 65.50%。
- 在本次全部计时 trace 中，StartLux 直接、Qwen 直接及两条级联的**最终标签**在各自工作负载上均保持一致；CLINC/Kev 直接也保持一致。这里的“一致”针对观测到的重复，不是任意未来批次的确定性保证。

三种模型在该 200 条子集上的正式预测准确率与 c1 实测相同：CLINC 为 Kev 80.0%、StartLux 94.5%、Qwen 88.5%；SQuAD 为 81.0%、93.0%、87.5%。这些值与完整测试报告的 600/2,000 条准确率不同，主要因为子集不同；不能把性能子集替换成最终质量评估。

## 5. 显存、单卡时间与统计边界

60 个计时单元的显存记录均来自同一个 GPU UUID。每个单元记录了 45–81 次采样；最小记录空闲比例为 **16.52%**，对应峰值使用 **38,458 / 46,068 MiB**，发生于 SQuAD/Kev → Qwen 的 8 并发单元。所有单元的采样摘要均满足 10% 空闲要求。

原始逐时显存样本没有进入归档，只有每轮摘要。独立复核核对了采样数量、设备 ID、峰值使用与最低空闲比例的算术一致性；这些摘要不能证明采样间隔内不存在更短的显存峰值。单卡双模型组合的显存余量也明显小于直接服务。

`allocated_gpu_seconds_per_1000` 是计时区间中每 1,000 条输入占用单张已分配 GPU 的 wall-clock 秒数。例如 c8 下，StartLux 直接在 CLINC/SQuAD 分别约为 16.92/17.28 秒，Qwen 为 30.57/32.51 秒。它不等于 kernel busy time，也没有计入模型启动、预热、空闲或存储，因此不是完整账单或美元成本估计。

三轮重复共享硬件、样本和服务过程，部署顺序没有随机化。这里报告均值与范围，不把 60,200 次循环请求当成 60,200 个独立准确率样本，也不从三个轮次构造看似精确的性能置信区间。结果限于当前冻结的 BF16 服务实现、预热条件、单卡和封闭循环负载；开放到达流量下的排队、长期稳定性和跨机器波动仍没有测量。
