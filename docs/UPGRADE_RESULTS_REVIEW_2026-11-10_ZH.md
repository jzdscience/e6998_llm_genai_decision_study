## Claude 分析需要收窄的解释

1. **容量表述。** “最高通过的已测速率为 40”在协议定义下正确，但不是连续稳定容量 40。
   4B 的 20/s 异常轮在 500 ms 和 1,000 ms 下均未达到 99%；原样保留，不挑选性重测。
2. **准确率比较。** 实时成功子集准确率与历史整池结果接近，不表示等价或逐条相同。
   应使用现成的 matched-subset historical accuracy，保留相同输入及出现次数的权重。
   3,200 个输入中出现多个实时标签的数量分别为 4B 33、9B 19、级联 49；原因没有单独分离。
   级联“约 73.5–74.6%”近似各速率三轮中位数的范围，实际逐单元范围是 73.43–75.80%，须注明汇总口径。
3. **预检显存归因。** graph profile 0.39 → 0.25 GiB 与 KV 2.45 → 2.93 GiB 是共同观测，
   不能把全部 KV 变化归因于 graph 内存下降。正式单元的 KV 也会变化，须使用每个单元实际日志。
4. **强制级联计时。** 强制转交的 SLO 是两级调用与客户端调度/排队共同产生的端到端结果，
   不是只测 Qwen 生成耗时。它验证开发并发可运行，不替代正式约 24% 转交政策的性能。
5. **148 秒重叠。** `_overlap_seconds` 对不同请求的前后级 HTTP stage 区间两两求交并累计，
   可能重复计时。因此 148 秒不是 30 秒预检中的双引擎并行墙钟时长，也不能证明 GPU kernel 重叠。
   独立重算的两两交集累计为 147.9986 秒，两个接口同时有请求在途的区间并集为 14.7769 秒。

全部成功 offers 的匹配比较如下；重复输入按实际出现次数计权，不是新增独立质量评估样本。

| 部署 | 实时准确率 | 同一成功子集的历史准确率 |
|---|---:|---:|
| StartLux-4B | 74.1741% | 74.1237% |
| StartLux-9B | 76.6448% | 76.6401% |
| 级联 | 74.1188% | 74.3419% |

4B 20/s 异常的可复核边界更具体：78 个超过 500 ms 的请求，其计划 arrival 覆盖
110.6489–114.2715 秒（跨度 3.6226 秒）。这些请求的客户端排队中位 1,271.92 ms，worker 计时中位
228.20 ms，记录的模型调用中位 225.32 ms；最大 dispatch lag 为 162.52 ms。
其中 worker 计时减去模型调用计时的最大值为 2,896.75 ms，说明存在调用计时之外的明显等待。
代码中 trace 写入与 worker 起止计时共享锁，但这不能单凭现有 trace 确定 I/O、锁竞争或 OS 调度的根因。
“3.7 秒”应描述受影响请求到达区间的大致跨度，不应写成精确测得的整机停顿时长。
该单元另有一次客户端拒绝；500 ms 及时率 96.875%，1,000 ms 及时率 97.231%。
