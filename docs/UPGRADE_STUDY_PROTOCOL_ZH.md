# StartLux9B 服务成本：升级前级还是加后级

协议 ID `anli-upgrade-service-v1`，机器可读版本为
[configs/upgrade_study_protocol.json](../configs/upgrade_study_protocol.json)。

- 2026-11-08 初稿：`9cb3274`。
- 2026-11-08 按 Codex 复审（[UPGRADE_STUDY_REVIEW_2026-11-08_ZH.md](UPGRADE_STUDY_REVIEW_2026-11-08_ZH.md)
  的 U1–U5）修订，并据此实现 `decision_study/upgrade_study/`。

正式测量前还需三步：本机软件验收（Codex 交叉检查实现提交）、节点开发预检、最终运行绑定。预检失败时保留
证据，修订配置版本后重新预检，不在同一身份下自动调整份额。

## 要回答的问题

在 ANLI 上，StartLux-9B 直接预测为 76.69%，StartLux-4B 为 74.19%，以 Qwen3.5-9B 为后级的冻结级联最高为
74.41%（class_conditional，测试集转交 23.94%）。这些都是顺序采集得到的质量数字，没有任何一个 9B 部署测过
服务成本。本实验在同一张 L40S、同一 ANLI 工作负载、同一到达过程和同一客户端口径下，比较三种部署：

| 条件 | 部署 | 离线质量（回顾性） | 显存份额合计 |
|---|---|---|---:|
| `startlux4b` | StartLux-4B 直接预测 | 74.19% | 0.40 |
| `startlux9b` | 升级前级：StartLux-9B 直接预测 | 76.69% | 0.50 |
| `cascade` | 加后级：StartLux-4B 前级，按 V3 冻结的 class_conditional 政策转交 Qwen3.5-9B | 74.41% | 0.90 |

主要回答两件事：在每个到达率下，哪种部署每秒给出更多及时且正确的回答；每种部署在测试的速率里，所有三轮都
至少 99% 请求及时成功的最高速率是多少。三种部署的总显存份额和计算量不同，比较的是三种明确的部署方式，
不能据此单独识别模型大小、架构、训练或双模型驻留的因果效应。

## 条件与政策选择

`startlux4b` 是两种选择共同的起点。`startlux9b` 用 StartLux-9B 替换 4B；`cascade` 保留 4B，并让一个 9B
生成式模型处理被转交的请求。两个 9B 的份额都是 0.50，这只让两边的 9B 预留相同，不代表两种部署总资源相等。

本研究回顾性选择了 class_conditional 这一固定部署；随后冻结，不用新服务结果再选择政策、阈值或部署配置。
它是 V3 已测政策中离线准确率最高者，不保证服务 goodput 最高，也不是级联服务性能的上界。confidence 政策的
转交量相近（743 对 766 题），V3 的主政策 positive_gain 冻结为零转交，都不另跑。不加双模型闲置驻留条件，也不从
V2 的 4B+4B 结果推断 4B+9B 驻留没有代价。

## 部署配置与显存

三种部署沿用 V3 与规模对照的推理设置：vLLM 0.31.0、BF16、`max_model_len` 8192、关闭 prefix caching 和
chunked prefill、StartLux 前端 `--max-inflight 16`、Qwen 关闭 thinking 并用受约束的 JSON 标签输出（最多 64
个 token）。模型 revision 固定为 StartLux-4B `416088f7`、StartLux-9B `18a17f73`（原生温度 1.1014）、
Qwen3.5-9B `c2022362`。权重只读复用已有快照：4B 来自 V1 安装，StartLux-9B 来自规模对照（另按规模对照协议
核对三个元数据文件的 SHA），Qwen-9B 来自 V3；运行时锁直接取自 V3 与规模对照的冻结计划，只改显存份额。

下表的 KV 容量是按已有单模型日志外推的估算，需要预检实测。两份 9B 日志都来自单模型 0.80 运行：引擎可见
显存 44.39 GiB，0.80 对应 35.51 GiB；StartLux-9B 权重 16.8 GiB、KV 15.76 GiB、activation 峰值 2.57 GiB、
CUDA graph 0.24 GiB，Qwen-9B 分别为 16.8、17.05、1.27、0.24 GiB。

| 模型 | 份额 | 预算 | 估算 KV（待实测） |
|---|---:|---:|---:|
| StartLux-4B | 0.40 | 17.76 GiB | 约 7.6–8.3 GiB（已有 0.40 运行实测） |
| StartLux-9B | 0.50 | 22.20 GiB | 约 2.6 GiB |
| Qwen3.5-9B | 0.50 | 22.20 GiB | 约 3.9 GiB |

vLLM 0.31.0 的 `--gpu-memory-utilization` 是每个实例的预算，0.40 + 0.50 符合参数语义；份额之和不能证明两个
实例能同时启动并在并发下正常工作，正式收据记录实际的 CUDA 总量、预算、KV 容量和进程显存。

## 双服务生命周期

`cascade` 需要 4B 与 9B 同卡驻留。V1 的双模型启动器要求每个模型不超过 0.40；本实验不沿用任何 V1 gate，
改由新的控制器依次启动两个单模型服务，并显式承担以下约定：

1. 第一个服务启动前核实当前 Slurm allocation、单张 L40S，并要求 GPU 上没有任何 compute 进程。
2. 第二个服务启动前，GPU 上只允许本次已启动前级的进程组及其后代，出现其他进程即停止，不终止它们。
3. 三个角色各用独立的 runtime-control 目录（V1 会在控制目录写 `last_services.json`），端口按模型区分并记录。
4. 两个服务放在同一个外层清理栈里：后级启动失败、测量出错、超时或被中断时，都停止已启动的自有进程组。
   CLI 把 SIGTERM/SIGHUP 转为中断，同样走清理路径。
5. 每个单元结束后确认自有进程组已退出、GPU 上没有 compute 进程，再进入下一个单元。
6. 不嵌套 `size_control.runtime_context`（它每次进入都拒绝任何已有 GPU 进程），不改写 V3 或规模对照的控制
   记录；新输出目录绑定新协议、源码、环境与模型身份，旧运行时、安装记录和锁只读复用。

## 开发预检

预检在正式单元之前进行，覆盖三种最终部署，使用正式启动命令、份额、token 上限和并发设置，不读 test gold：

1. 每个角色对全部 3,200 条正式输入和 90 条开发输入做 tokenizer 长度检查，要求不截断且留出输出预算。
2. 每种部署对 90 条开发输入做串行接口检查；`cascade` 对每条输入依次调用两个模型。
3. 每种部署再跑一份事先固定的并发开发调度（16 worker，10 请求/秒，30 秒）。`cascade` 在这一步对每个请求
   强制转交，保证两个引擎确实同时工作；这些请求标为 `preflight_forced_deferral`，只存于预检目录，
   不进入正式 trace，也不改变正式政策。
4. 记录实际启动参数、KV 容量、GPU 进程与显存、health、错误和 preemption 计数。
5. 服务启动失败、OOM、引擎退出、接口或长度错误、并发调度中出现任何 error/timeout/deadline、检查后 health
   失败都判失败，停止并保存证据。`cascade` 另要求两个引擎的工作时间有重叠，且每条成功请求的路由原因都是
   `preflight_forced_deferral` 并实际调用了后级。
   预检不比较 goodput，不因未达到 500 ms 或合法的标签差异调整任何设置。

三份预检收据都为 PASS 后才能开始正式测量，收据哈希绑定进每个单元的计划。

## 工作负载、到达与客户端

| 项目 | 设置 |
|---|---|
| 输入 | V3 的 3,200 道 ANLI test，与 V3、规模对照同一批 ID 与文本；每轮按固定种子打乱后循环使用 |
| 预热 | 每个单元启动服务后串行调用 90 条开发输入；`cascade` 对每条输入依次调用两个模型 |
| 到达率 | 10、20、40、80 请求/秒，Poisson 到达 |
| 时长与重复 | 每单元 120 秒，3 轮；同一（轮次，速率）下三种条件使用同一份到达表与样本顺序 |
| 顺序 | 每轮内速率顺序按固定种子打乱；同一（轮次，速率）的三个条件紧挨着执行，顺序也按固定种子打乱 |
| 隔离 | 每个单元重新启动服务并预热，结束后停止并确认后端退出 |
| 客户端 | 16 个 worker，最多 64 个在途加排队；每个模型调用最多一次 HTTP |
| 执行预算 | worker 开始执行时给出 `min(30 秒, drain 剩余时间)`，客户端排队不计入这 30 秒 |
| SLO 计时 | 从预定到达到最终回答完成，包括客户端排队 |

`cascade` 的一个请求先调用 StartLux-4B。前级成功时，把响应的模型角色显式规范为 `startlux4b`（服务启动时已
核验其 checkpoint），交给 `decision_study.v3.policies.route` 和完整的冻结政策对象
（`policies.qwen9b.class_conditional`，阈值 `0.272907934835248`，冻结文件 SHA `28efefe7…`）。路由输入格式
不符时记为 `router_input` 错误，不转交；前级调用本身失败时按 V3 规则强制转交。两阶段共享一个单调时钟截止
时间，后级只获得剩余预算；预算用尽时记为 `deadline`，不再调用后级。后级失败就是这个请求失败，不回退成
前级答案。每个 offer 记录前后两级各自的 request ID、状态、耗时、概率、路由分数与原因和最终标签。HTTP
超时之外，外层 watchdog 给整个单元设硬期限。

共 36 个单元，正式到达窗口 72 分钟。按已测启动时间（4B 约 2 分钟，9B 约 4 分钟，`cascade` 约 6 分钟）和
每单元的预检、预热、drain，预计 4–5 小时，这是计划估计；支持换 allocation 续跑，每次读取实际剩余时间。

## 指标与比较

主指标是 500 ms SLO 下每秒及时且正确的回答数（correct goodput），逐条用真实返回标签判定，分母为 120 秒；
每个条件 × 速率报告 3 轮的中位数和最小、最大值。同一批 trace 还给出 1,000 ms SLO 下的同一指标（只有实际
转交的请求会调用后级），以及全部 offer、接纳、成功、及时成功、正确、及时且正确、拒绝、失败、晚返回、
p50/p95/p99、实际转交率、GPU 显存峰值与利用率、启动时间。

比较方式预先固定为：

1. 每个速率下 `startlux9b` 与 `cascade` 的 correct goodput（配对到达表），同时列出 `startlux4b`。
2. 每个条件在测试速率中所有三轮都至少 99% offer 及时成功的最高速率。全部速率都达标时写“已测至 80 均达标”，
   都不达标时写“已测速率中未找到”，不称为最大稳定容量。
3. 与历史记录对照：按本次实际 offer 和成功响应的 ID 及出现次数加权，分开报告完整历史池的准确率、匹配
   子集的历史准确率和本次结果；保存实时标签、概率、路由与历史记录的差异和重复请求的变化。

历史重放（3,200 条完整池，class_conditional 766 题、confidence 743 题）只作为回归检查，在准备阶段执行。
每单元只覆盖部分题目，过载拒绝还会改变成功样本的组成，所以不要求实时准确率等于离线值，也不要求实时转交
数等于 766；合法差异不触发调阈值、丢弃轮次或补跑。只有 3 轮，结果按描述性报告，不做显著性检验；结论限定
在测试的速率和这套客户端、vLLM 设置。

## 边界

1. ANLI test 已在 V3 中评价过，质量部分是回顾性的。
2. 只测一种 GPU 和一套客户端与 vLLM 设置，容量会随设置变化；不换算美元成本，资源以显存预算、采样显存和
   GPU 时间描述。
3. 跨 allocation 续跑时记录每个单元的节点与 GPU，单列跨 allocation 的配对组。

## 运行

审核通过并完成节点预检后，在节点的干净源码 checkout 中执行
`bash scripts/run_upgrade_study.sh <runtime-root> [--new-allocation] [--resume-interrupted]`。脚本依次初始化运行时、
准备输入、预检、正式测量、评价和导出，详见 [RUN_UPGRADE_STUDY_ZH.md](RUN_UPGRADE_STUDY_ZH.md)。
