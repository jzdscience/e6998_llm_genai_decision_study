# StartLux9B 服务成本：升级前级还是加后级（设计稿，待审）

2026-11-08，协议 ID `anli-upgrade-service-v1`。机器可读草案为
[configs/upgrade_study_protocol.json](../configs/upgrade_study_protocol.json)。本文是待 Codex 审核的设计，
尚未实现、没有运行任何模型；审核通过后再写代码和运行入口。

## 要回答的问题

在 ANLI 上，StartLux-9B 直接预测为 76.69%，StartLux-4B 为 74.19%，以 Qwen3.5-9B 为后级的冻结级联最高为
74.41%（class_conditional，测试集转交 23.94%）。这些都是顺序采集得到的质量数字，没有任何一个 9B 部署测过
服务成本。本实验在同一张 L40S、同一 ANLI 工作负载、同一到达过程和同一客户端口径下，比较三种部署：

| 条件 | 部署 | 已知质量（回顾性） |
|---|---|---|
| `startlux4b` | StartLux-4B 直接预测 | 74.19% |
| `startlux9b` | 升级前级：StartLux-9B 直接预测 | 76.69% |
| `cascade` | 加后级：StartLux-4B 前级，按 V3 冻结的 class_conditional 政策转交 Qwen3.5-9B | 74.41% |

主要回答两件事：在每个到达率下，哪种部署每秒给出更多及时且正确的回答；每种部署在测试的速率里最高能稳定
承受多少请求。质量方面只做一致性核对，确认实时服务的输出与离线结果一致。

## 为什么是这三个条件

`startlux4b` 是两种选择共同的起点。`startlux9b` 与 `cascade` 都只多用一个 9B 模型，区别在于 9B 是作为前级
替换 4B，还是作为生成式后级处理一部分请求。

级联政策用 class_conditional，因为它是 V3 里准确率最高的冻结级联，相当于给“加后级”最有利的版本。这个选择
知道测试集结果，报告中会写明。confidence 政策的转交量相近（743 对 766 题），不另跑。V3 的主政策
positive_gain 冻结为零转交，服务上与 `startlux4b` 加一个闲置后级相同，也不另跑。

不纳入的条件：双模型驻留但只调用 4B（V2 在 4B+4B 上没有测到驻留本身的代价，属于分解问题，不在最小对照内），
以及 Qwen-9B 直接预测（66.22%，不是这里比较的部署选项）。

## 部署配置与显存

三种部署都沿用 V3 与规模对照的推理设置：vLLM 0.31.0、BF16、`max_model_len` 8192、关闭 prefix caching 和
chunked prefill、StartLux 前端 `--max-inflight 16`、Qwen 关闭 thinking 并用受约束的 JSON 标签输出。模型
revision 固定为 StartLux-4B `416088f7`、StartLux-9B `18a17f73`（原生温度 1.1014）、Qwen3.5-9B `c2022362`。
权重直接复用已有快照（4B 来自 V1 安装，StartLux-9B 来自规模对照，Qwen-9B 来自 V3），不重新下载。

| 模型 | 显存份额 | 预留 |
|---|---:|---:|
| StartLux-4B（`startlux4b` 与 `cascade`） | 0.40 | 18.0 GiB |
| StartLux-9B（`startlux9b`） | 0.50 | 22.5 GiB |
| Qwen3.5-9B（`cascade`） | 0.50 | 22.5 GiB |

份额依据已有引擎日志。9B 模型加载占用 16.8 GiB；份额 0.80 时可用 KV cache 为 15.8–17.1 GiB，可推出权重之外的
开销约 2.2–3.4 GiB。份额 0.50 时 KV cache 约 2.3–3.5 GiB，约 6 万到 9 万个 token，可容纳 7 条以上 8,192 token
的序列，ANLI 提示最长约 360 token。份额 0.40（18.0 GiB）时 KV cache 不足，9B 无法启动。

两个 9B 用同样的 0.50，是为了让 `startlux9b` 和 `cascade` 里的 9B 拥有相同预留。规模对照里 StartLux-9B 用的是
0.80；份额只影响 KV 容量，在前端最多 16 个在途请求、客户端最多 64 个在途请求的条件下不构成瓶颈。实时输出会
逐题对照规模对照的预测。

`cascade` 需要 4B 与 9B 同卡驻留，合计预留 0.90（40.5 GiB / 45.0 GiB）。V1 的双模型启动器规定每个模型不超过
0.40，其报错说明这条规则是为了避免在另一种显存设置下悄悄沿用已校准的 gate。本实验不沿用任何 V1 gate，
只使用 V3 为 ANLI 冻结的政策，因此改为依次启动两个单模型服务（先 4B、后 9B），两个份额都记录在运行证据里，
不修改 V1 冻结代码。

正式测量前先做一次可行性检查：按 `cascade` 配置启动两个服务，用 90 条开发输入串行调用两个模型，记录显存。
若 Qwen-9B 在 0.50 下无法启动或开发调用出错，就停止并保留证据，不自动改用其他份额，需另行修订协议。

## 工作负载、到达与客户端

| 项目 | 设置 |
|---|---|
| 输入 | V3 的 3,200 道 ANLI test，与 V3、规模对照同一批 ID 与文本；每轮按固定种子打乱后循环使用 |
| 预热 | V3 的 90 条开发输入，串行；`cascade` 的预热对每条输入依次调用两个模型 |
| 到达率 | 10、20、40、80 请求/秒，Poisson 到达 |
| 时长与重复 | 每单元 120 秒，3 轮；同一（轮次，速率）下三种条件使用同一份到达表与样本顺序 |
| 顺序 | 每轮内条件顺序、条件内速率顺序按固定种子打乱 |
| 隔离 | 每个单元重新启动服务并预热，结束后停止，避免过载单元的积压带入下一个单元 |
| 客户端 | 16 个 worker，最多 64 个在途加排队；每个模型调用只发一次 HTTP；每个请求总超时 30 秒；drain 60 秒 |
| 计时 | 从预定到达到最终回答完成，包括客户端排队；`cascade` 包括前级、路由和可能的后级调用 |

`cascade` 的每个请求先调用 StartLux-4B，再把它的概率交给 `decision_study.v3.policies.route` 和冻结政策
（`policies.qwen9b.class_conditional`，阈值 0.2729）。判定转交时用剩余时间调用 Qwen-9B，以 Qwen 的标签作为
最终回答；前级调用失败时按 V3 规则强制转交。离线重放已确认：用 V3 保存的 StartLux-4B 测试集预测，这个函数
正好转交 766 题（23.94%），confidence 政策为 743 题，与 V3 报告一致。

共 36 个单元，正式到达窗口 72 分钟。按已测启动时间（4B 约 2 分钟，9B 约 4 分钟，`cascade` 约 6 分钟）和每单元
的预检、预热、drain，预计总时长 4–5 小时，可在一次 allocation 内完成，也支持换 allocation 续跑。

## 指标与比较

主指标是 500 ms SLO 下每秒及时且正确的回答数（correct goodput），每个条件 × 速率报告 3 轮的中位数和最小、
最大值。次要指标从同一批 trace 计算：1,000 ms SLO 下的同一指标（级联必然包含两次调用，较宽的 SLO 给它公平的
机会）、及时比例、每秒完成数、p50/p95/p99、拒绝数、实际转交率、GPU 显存峰值与利用率、启动时间。

比较方式预先固定为：

1. 每个速率下 `startlux9b` 与 `cascade` 的 correct goodput（配对到达表），同时列出 `startlux4b`。
2. 每个条件在测试速率中，所有轮次都至少 99% 请求及时的最高速率。
3. 一致性核对：成功回答的准确率与离线结果对照（74.19%、76.69%、74.41%）；`cascade` 每题的转交决定与
   V3 离线决定对照；重复请求的标签变化。

只有 3 轮，结果按描述性报告，不做显著性检验；结论限定在测试的速率、这套客户端和 vLLM 设置。

## 边界

1. ANLI test 已在 V3 中评价过，质量部分是回顾性的；本实验不据此选择模型、阈值或政策。
2. 只测一种 GPU、一套客户端与 vLLM 设置，容量会随这些设置变化；不换算美元成本，资源以显存预留和 GPU 时间描述。
3. 若跨 allocation 续跑，按服务实验的做法记录每个单元所在的节点和 GPU，并单列跨 allocation 的配对组。

## 实现计划（审核通过后）

新建 `decision_study/upgrade_study/`，复用服务实验的测量代码（`run_cell`、`summarize`、`verify_cell`、
`ResourceMonitor`）、V3 的 `route` 和 V3/规模对照的运行时写法，不修改 V1 冻结代码或已验收实验的代码。
提供一条节点命令 `bash scripts/run_upgrade_study.sh <runtime-root> [--new-allocation]`，可续跑，结束后导出结果包。
本机测试覆盖：假服务下的级联路由与超时、计划与到达表的确定性、766 题离线重放、在合成 trace 上的评价。

## 请审核者重点看的问题

1. 两个 9B 都用 0.50，而规模对照的 StartLux-9B 用过 0.80。
2. 速率 10/20/40/80、每单元 120 秒、3 轮是否足够；是否需要加一档 60。
3. 级联用 class_conditional 还是 V3 预定的对照 confidence。
4. 主 SLO 500 ms 加次要 1,000 ms 是否合适。
5. 每单元重启服务（约多 2 小时）与每轮重启之间的取舍。
